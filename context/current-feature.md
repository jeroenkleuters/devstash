# Current Feature: Collection Create

## Status

In Progress

## Goals

- The top bar's **New Collection** button stops being display-only: it opens a modal with the fields a collection needs (name, description).
- Collections are created for the signed-in user only — `userId` comes from the session, never from the request.
- A collection is created through a server action validated with Zod, mirroring `createItem`: `{ success, data, error }` back, no throw on a rejected write.
- Reads stay in `src/lib/db/collections.ts` and are called from server components; any client-side read goes through an API route, as `GET /api/items/[id]` does for the drawer.
- Success shows a toast and closes the modal; failure shows a toast and leaves the form open with what was typed.
- Everything showing collections updates on save — the dashboard's collection grid, the sidebar's Favorites/Recent lists and the Collections stat cards — via `router.refresh()`, since all three are server-rendered.

## Notes

- **Follow the item create flow file-for-file.** `ItemCreateDialog` (controlled `Dialog`, Radix unmounts the content on close so the next open starts empty) + `ItemCreateForm` (`.catch(() => null)` around the action so a failed *request* cannot strand `saving`) + `createItem` in `src/actions/items.ts` + `createItem` in `src/lib/db/items.ts` + `createItemSchema` in `src/lib/validations/item.ts`.
- **Create is a server action, not an API route.** The request asked for "api routes for any client-side calls"; in the items pattern that means client-side *reads* (the drawer's `GET /api/items/[id]`), while mutations are server actions — which is also what coding-standards mandates for form submissions. Building create as an action is the reading that matches both. Flagging it rather than assuming: say so if a `POST /api/collections` was actually wanted.
- `Collection` needs **no migration** — `name`, `description`, `isFavorite`, `defaultTypeId` and the `userId` relation have been in the schema since `20260814120000_init`.
- `description` is `String?`, so an emptied field stores `null` rather than `""` — the same rule `updateItemSchema` already encodes.
- `defaultTypeId` exists in the schema but nothing in the app sets or reads it. Out of scope unless asked; a collection is created without one.
- `src/lib/db/collections.ts` has **no write function yet** — every export there is a read narrowing the `cache()`d `getCollections`. The new `createCollection` sits alongside them, and the `cache()` memoization is per-request so it cannot serve a stale list after the write.
- Free-tier limits (3 collections) are **not** enforced anywhere in the app — per project overview §8 all users get full access during development. Not part of this feature.
- The trigger lives in `src/components/layout/top-bar.tsx`, which is a **server component**: `DialogTrigger asChild` clones its child, so the button must be constructed inside the client dialog component and the caller passes a `label` string, exactly as `ItemCreateDialog` documents.
- Toasts go through `sonner`, already mounted once in the root layout.
- Markup carries no Tailwind utility classes; any new styling is a semantic class in `globals.css`.
- Testable surface is the schema and the action (`src/lib/validations/**`, `src/actions/**` are what Vitest collects) — the dialog and form are components and are out of scope by configuration.

- **2026-08-18 — Auth phase 2: credentials (email/password).** Email/password sign-in and registration now sit alongside GitHub OAuth. Four files: `src/lib/validations/auth.ts` (new), `src/app/api/auth/register/route.ts` (new), plus edits to `src/auth.config.ts` and `src/auth.ts`. **No migration** — `User.passwordHash` already existed from the initial schema (`String?`, null for OAuth-only accounts), so the spec's conditional "add password field" requirement was already satisfied; `npm run db:status` stayed clean throughout. **`zod` (^4.4.3) became a direct dependency** — it was absent despite coding-standards mandating it and project overview §7 planning `lib/validations/`; it was already in the tree transitively, which is why `npm install zod` reported "up to date" while still adding the entry. Zod 4 idioms differ from 3: `z.email()` is top-level rather than `z.string().email()`, and refine params take `error` rather than `message` (the latter still works, migrated internally by `normalizeParams`). **The split pattern held:** `auth.config.ts` declares `Credentials({ authorize: () => null })` so both runtimes agree on the provider list, and `auth.ts` swaps in the real provider. The swap needed a `withRealCredentials` helper rather than a one-line `.map`, because providers come in two shapes — `GitHub` is passed as a bare *function* with no `id`, while `Credentials(...)` is an already-called config object that has one; a naive `p.id === "credentials"` test throws on the function. The proxy never runs `authorize` (it only verifies the JWT) and its matcher is `/dashboard*`, so it never intercepts `/api/auth/*`; the placeholder is therefore unreachable in practice. **`/api/auth/register` coexists with the `[...nextauth]` catch-all** because a static App Router segment outranks a sibling catch-all — no config needed. The route validates with Zod, returns `{ success, data, error }`, and hashes at 12 rounds to match `prisma/seed.ts`. **Emails are trimmed and lowercased before the format check**, in one shared `emailSchema` used by both sign-in and registration — without it a `Test@Example.com` registration creates a row that `test@example.com` can never sign into; verified by confirming `TEST@Test.com␣␣` is caught as a duplicate. The duplicate pre-check is racy, so a `Prisma.PrismaClientKnownRequestError` / `P2002` catch backstops it with the same 409 (imported from `@/generated/prisma/client` as `Prisma.` — not the `internal/prismaNamespace` path, which also exports it but is private). **A `/feature review` pass found three issues, all fixed before merge.** (1) An unused `RegisterInput` export — dead per coding-standards, removed; phase 3's register form can re-add it. (2) **bcrypt silently truncates at 72 bytes**, confirmed locally: a 72-byte hash accepts an 86-byte password sharing its first 72 bytes, so a long passphrase would be interchangeable with a truncated variant. The register schema now rejects over-length passwords instead, counting **UTF-8 bytes via `TextEncoder`** rather than `.length`, since one character can encode to four. (3) **A ~235 ms timing oracle on sign-in:** returning early on an unknown email skipped bcrypt entirely, and bcrypt at 12 rounds costs ~220 ms, so response time leaked whether an address was registered — measured live at 0.354 s (registered) vs 0.127 s (unknown), a gap far larger than network jitter. Fixed by comparing against a constant throwaway 12-round hash (`ABSENT_PASSWORD_HASH`) whenever there is nothing real to match, which levels every rejection path; re-measured at 0.354 / 0.353 / 0.350 s for registered / unknown / OAuth-only. Note the register endpoint still leaks the same fact outright via its 409, but that is spec-mandated UX, not a defect. **One false trail worth remembering:** a 19-emoji (76-byte) password appeared to pass the new cap when posted through Git Bash with `curl -d`, which mangles multibyte input before curl sends it — Node confirmed the schema computed 76 bytes and rejected correctly, and re-posting via `--data-binary @file` returned the expected 400. Test multibyte payloads from a file on this shell, never inline. **Verified end to end** against the Neon dev branch: registration 201; duplicate (incl. case/whitespace variants) 409; mismatch, short password, over-length password, bad email, blank name and non-JSON all 400 with the right message; sign-in with a registered account *and* with the seeded `demo@devstash.io` / `12345678` both reach `/dashboard` with the real user id on the session; wrong password, unknown email and an OAuth-only account (no `passwordHash`) all return `CredentialsSignin`; GitHub's authorize redirect stays well-formed; and the browser flow renders both providers on the built-in sign-in page. **Still out of scope and worth deciding before phase 3:** the dashboard continues to render the demo account because `src/lib/db/user.ts` is unchanged, so it shows "Demo User" no matter who signs in; there is **no rate limiting** on either endpoint, leaving brute-force wide open; a GitHub-linked email gets a 409 on register and cannot add a password, which is account-linking territory; and no custom login/register UI exists. Testing left four accounts in the dev branch (`test@test.com`, `two@test.com`, `cap72@test.com`, `capemoji@test.com`) — harmless, but they inflate any user count until removed. - **2026-08-24 — Direct-to-R2 uploads with a 100 MB cap.** Uploads stopped passing through the app: `POST /api/upload` no longer *takes* the file, it *authorises* one — JSON metadata in, a 5-minute presigned PUT out — and the browser sends the bytes straight to the bucket. Three new files (`src/components/items/item-copy-button.tsx`, `src/lib/item-copy.ts` + its test), five edited, **no migration**, **no new dependency** and **no new ShadCN primitive** — `sonner` came with the rate limiting. **The decision that shaped everything is where the payload comes from.** `ItemSummary` carries no `content` or `url`, so the button **fetches the detail on click** through the existing `GET /api/items/[id]` — the same route the drawer uses — rather than widening the shared `itemSelect`, which would pull full snippet text (`@db.Text`) into every dashboard and type-page query and ship it to the browser for every row, copied or not. The cost is a round trip before the toast, **measured at ~475–520ms warm in dev against remote Neon** (the route itself 459/461ms), and during it the button is disabled but looks unchanged — a spinner or pressed state on `busy` is the fix if that ever reads as unresponsive. **The gate is the type slug, not `contentType`:** `ItemTypeSummary` carries no content type, and a file and an image are both `ContentType.FILE` whose payload is an R2 object key that means nothing on a clipboard — so `isCopyableType` joins `isCodeType` / `isMarkdownType` / `uploadKindFor` in `src/constants/item-types.ts`, deriving from `uploadKindFor` rather than becoming a fourth parallel list. Those two types get **no button rather than a dead one**. **The button is a sibling of the stretched `.item-card-open` hit target, not a child** — a button cannot nest in a button — with `z-index: 2` putting it on top, which is exactly the shape `file-row.tsx` already uses for its download link; a click never reaches the card, so **no `stopPropagation` is involved**, and hovering the button does not tint the card, which is the honest feedback that this click does something else. **`setBusy(false)` runs in a `finally`**, so a failed request cannot leave the button permanently dead — the identical defect that stranded the delete dialog (found in the browser) and later the edit form, and the reason it was written that way the first time here. `copyText` moved out of `item-drawer-actions.tsx` into `src/lib/item-copy.ts` so the drawer and the card share one rule rather than two that can drift. **6 new tests take the suite 195 → 201**, and the one that matters pins the `||`: an emptied content field is a field with nothing in it, and swapping the operator for `??` would return `""` and report a successful copy of nothing. **Proven non-vacuous rather than assumed** — making that swap failed exactly the two empty-string cases while the other four still passed, and it was reverted. CSS-wise the button is `opacity: 0` at rest, revealed by `.item-card:hover` (not the `:has(.item-card-open:hover)` the border tint uses, so hovering the button itself keeps it visible) and by its own `:focus-visible`; it is **still in the tab order while invisible**, so the focus rule is what makes it reachable rather than a convenience. The check is held at `opacity: 1` for its two seconds, since the pointer has usually left by then and a confirmation that vanishes with it confirms nothing. **Verified in the browser** as demo against the Neon dev branch, reading the DOM rather than screenshots: opacity `0 → 1 → 0 → 1` across rest / card hover / pointer leave / keyboard focus; the clipboard genuinely changed from a sentinel to the real snippet source, a link's `https://www.nrc.nl/` and a note's markdown; exactly one `GET /api/items/{id}` → 200 per click; `data-copied` held **2015ms** with the icon going `lucide-copy` → `lucide-check` → back and the colour `rgb(16,185,129)` (`--type-link`); the drawer never opened on a copy (including Enter on the focused button) while the card body still opened it on the right item. The dashboard's mixed Recent list is the decisive check for the gate — snippets 1/1, prompts 1/1, notes 2/2 with a button, files 0/3 and images 0/3 without — and across the type pages links 6/6, notes 2/2, prompts 4/4, commands 5/5, with `/items/files` and `/items/images` rendering their own components and zero copy buttons. **All four failure paths were exercised through `page.route()` with the source untouched**: 500, an aborted request, 401 and a 200 carrying empty content each produced the right message and, critically, **left the button re-enabled every time**. 390px showed `scrollWidth - innerWidth === 0` with the 28×28 button inside the card bounds and clear of the date; console clean, 0 errors and 0 warnings. Two screenshots were deleted afterwards — and note **`.playwright-mcp` holds two *tracked* `.yml` files** committed on 2026-08-18 before that path was gitignored, so artifact cleanup has to exclude them (a blanket `rm -rf` deleted them once before and needed `git checkout` to restore). **Three browser-tooling traps were recorded in `.claude/skills/feature/actions/browser.md`**, which is gitignored and so not in this commit: **never attach `page.on('request'/'response')` inside `browser_run_code_unsafe`** — it outlives the snippet, closes the MCP connection and resets the browser to `about:blank`, losing the signed-in session (it happened twice); wrap `window.fetch` through `page.evaluate` instead, re-installing after each navigation since it lives in the page; `route.fetch()` inside a handler that also calls `route.fulfill()` raises "Route is already handled!", so build a fixed body rather than relaying the real one; and **a generous `waitForTimeout` steps past transient state** — an 8-second wait read `data-copied: false` and no toast, which looked exactly like a silent failure when the copy had in fact succeeded and both had simply expired. **Left open:** there is no in-flight indicator during the ~0.5s fetch; the reveal is hover-based, so there is **no visible affordance on touch**, where the drawer's Copy stays the way in; each copy refetches with no detail cache, which is deliberate while nothing mutates an item but becomes worth revisiting alongside Favorite and Pin; and the button exists only on `.item-card`, so the file rows and gallery tiles have none. Everything the previous entries list stays open: Favorite and Pin are still the inert drawer actions, the edit drawer still cannot replace a file, downloads still stream through `/api/items/[id]/file`, `R2_PUBLIC_URL` is still unused, the seed still creates no tags, `/collections` still 404s, no CI runs the suite, and the `(app)` route group is still not adopted.
- **2026-08-26 — Audit fixes: the prune script's token filter and the duplicated item form fields.** A `code-scanner` pass over `src/`, `prisma/` and `scripts/` — run with the history's list of deliberate trade-offs as an explicit exclusion list, so it would not re-report fail-open rate limiting, the unused `R2_PUBLIC_URL`, Monaco's CDN, `consumeVerificationToken` still using `delete`, or `rankTypes` pulling every item row. **No High findings**, which is the honest result after the `auth-auditor` pass and the Redis migration: every route handler and server action already puts the session's `userId` in the Prisma `where`. Two things were real and both were fixed; four files changed, **no migration**, **no new dependency**, **no new ShadCN primitive**, and the suite stayed at **201 passing**. **The bug: `npm run db:prune` deleted the kept account's own password-reset token.** The exclusion was `identifier: { not: KEEP_EMAIL }`, but the reset flow namespaces its rows as `password-reset:<email>` (`passwordResetIdentifier` in `src/lib/password-reset.ts`), so demo's pending link did not equal `KEEP_EMAIL` and was swept with everyone else's — while a *verification* token for the same address, stored under the bare email, survived. `src/lib/account.ts` already gets this right for the account being deleted (`identifier: { in: [user.email, passwordResetIdentifier(user.email)] }`); the script simply never applied the mirror exclusion for the account being kept. **Confirmed live rather than by inspection, and the bug was present in the dev branch at the time**: it holds a `password-reset:demo@devstash.io` row left from the auth-audit testing, so the old filter deletes 3 tokens and the new one deletes 2. The fix is a shared `KEEPER_TOKENS` used by both the dry-run count and the delete, matching the bare address *or* anything ending in `:<address>` — which covers the current prefix and any later one, with the `:` stopping an address that merely *ends* in the kept one (`evildemo@devstash.io`) being preserved by suffix. **`passwordResetIdentifier` is deliberately not imported, and that was probed rather than assumed:** `@/lib/password-reset` reaches the Prisma singleton at import time, and imports hoist above the script's own `config({ path: [".env.local", ".env"] })` call, so importing it kills the run with `DATABASE_URL is not set` before `main()` starts.
