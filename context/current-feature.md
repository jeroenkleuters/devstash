# Current Feature: Item Drawer — Edit Mode

## Status

In Progress

## Goals

- The drawer's Edit button stops being inert: it switches the open drawer into edit mode inline, with no navigation and no second drawer.
- In edit mode the action bar is replaced by Save and Cancel. Cancel discards and returns to view mode; Save persists, returns to view mode, and the drawer shows the saved values.
- Title (required), Description and Tags (comma-separated) are editable for every type.
- Content (snippet / prompt / command / note), Language (snippet / command) and URL (link) appear only for the types that own them.
- Item type, collections and the created/updated dates stay display-only.
- `updateItem(itemId, data)` in `src/actions/items.ts` — a server action returning `{ success, data, error }`, validating with Zod, reading the session via `auth()` and enforcing ownership before it writes.
- `updateItem` in `src/lib/db/items.ts` does the write, replaces the item's tags, and returns the full updated `ItemDetail` so no second fetch is needed.
- Toast on save success and on failure; Save disabled while the title is empty.
- `router.refresh()` after a save so the card behind the drawer reflects the new title/tags.
- `npm test` and `npm run build` stay clean, with the new validation and action logic actually covered.

## Notes

Spec: @context/features/item-drawer-edit-spec.md

- **No `textarea` primitive exists yet** — `src/components/ui/` has `input` and `label` but nothing for multi-line. Adding the ShadCN `textarea` would be the tenth generated file there and needs no new dependency.
- **Tags are per-user rows**, not strings: `Tag` is `@@unique([userId, name])` with an implicit many-to-many to `Item`. So `connectOrCreate` has to key on the compound unique and carry `userId` — the spec's "disconnect all, connect-or-create" is right, but it cannot be written against `name` alone.
- **`getItemDetail` converts its dates to ISO strings** before they cross the wire. `updateItem` returns the same `ItemDetail` shape, so it must do the same conversion or the drawer will receive `Date`s from the action and strings from the API for the same type.
- **The drawer's detail lives in `ItemDrawerProvider`**, which currently only ever sets it from its own `fetch`. Save has to be able to replace it, so the context needs a way to hand a fresh `ItemDetail` back — and the provider's `requestRef` guard means a save landing while a fetch is in flight has to be reasoned about, not just assigned.
- **The mode has to reset when the drawer closes or switches items**, or clicking a second card would open it mid-edit on someone else's fields.
- **Validation is app-layer for the mutually exclusive fields** (`content` / `url` / `fileUrl`), per project overview §10 — the schema has no CHECK constraint, so the Zod schema is where "a link has a URL and no content" is enforced.
- Zod 4 idioms, as established in `src/lib/validations/auth.ts`: `z.url()` / `z.email()` are top-level, and refine params take `error` rather than `message`.
- Coding standards put this on a **server action, not an API route** — the drawer is authenticated and has a session to read, unlike the pre-auth flows that needed routes.
- FILE and IMAGE types are only partly served here: the spec gives them no editable payload field, so they get title / description / tags only. Uploads are a separate, Pro-gated feature.
- Out of scope per the spec: a code editor for the content textarea, collection management, and changing an item's type.

- **2026-08-18 — Auth phase 2: credentials (email/password).** Email/password sign-in and registration now sit alongside GitHub OAuth. Four files: `src/lib/validations/auth.ts` (new), `src/app/api/auth/register/route.ts` (new), plus edits to `src/auth.config.ts` and `src/auth.ts`. **No migration** — `User.passwordHash` already existed from the initial schema (`String?`, null for OAuth-only accounts), so the spec's conditional "add password field" requirement was already satisfied; `npm run db:status` stayed clean throughout. **`zod` (^4.4.3) became a direct dependency** — it was absent despite coding-standards mandating it and project overview §7 planning `lib/validations/`; it was already in the tree transitively, which is why `npm install zod` reported "up to date" while still adding the entry. Zod 4 idioms differ from 3: `z.email()` is top-level rather than `z.string().email()`, and refine params take `error` rather than `message` (the latter still works, migrated internally by `normalizeParams`). **The split pattern held:** `auth.config.ts` declares `Credentials({ authorize: () => null })` so both runtimes agree on the provider list, and `auth.ts` swaps in the real provider. The swap needed a `withRealCredentials` helper rather than a one-line `.map`, because providers come in two shapes — `GitHub` is passed as a bare *function* with no `id`, while `Credentials(...)` is an already-called config object that has one; a naive `p.id === "credentials"` test throws on the function. The proxy never runs `authorize` (it only verifies the JWT) and its matcher is `/dashboard*`, so it never intercepts `/api/auth/*`; the placeholder is therefore unreachable in practice. **`/api/auth/register` coexists with the `[...nextauth]` catch-all** because a static App Router segment outranks a sibling catch-all — no config needed. The route validates with Zod, returns `{ success, data, error }`, and hashes at 12 rounds to match `prisma/seed.ts`. **Emails are trimmed and lowercased before the format check**, in one shared `emailSchema` used by both sign-in and registration — without it a `Test@Example.com` registration creates a row that `test@example.com` can never sign into; verified by confirming `TEST@Test.com␣␣` is caught as a duplicate. The duplicate pre-check is racy, so a `Prisma.PrismaClientKnownRequestError` / `P2002` catch backstops it with the same 409 (imported from `@/generated/prisma/client` as `Prisma.` — not the `internal/prismaNamespace` path, which also exports it but is private). **A `/feature review` pass found three issues, all fixed before merge.** (1) An unused `RegisterInput` export — dead per coding-standards, removed; phase 3's register form can re-add it. (2) **bcrypt silently truncates at 72 bytes**, confirmed locally: a 72-byte hash accepts an 86-byte password sharing its first 72 bytes, so a long passphrase would be interchangeable with a truncated variant. The register schema now rejects over-length passwords instead, counting **UTF-8 bytes via `TextEncoder`** rather than `.length`, since one character can encode to four. (3) **A ~235 ms timing oracle on sign-in:** returning early on an unknown email skipped bcrypt entirely, and bcrypt at 12 rounds costs ~220 ms, so response time leaked whether an address was registered — measured live at 0.354 s (registered) vs 0.127 s (unknown), a gap far larger than network jitter. Fixed by comparing against a constant throwaway 12-round hash (`ABSENT_PASSWORD_HASH`) whenever there is nothing real to match, which levels every rejection path; re-measured at 0.354 / 0.353 / 0.350 s for registered / unknown / OAuth-only. Note the register endpoint still leaks the same fact outright via its 409, but that is spec-mandated UX, not a defect. **One false trail worth remembering:** a 19-emoji (76-byte) password appeared to pass the new cap when posted through Git Bash with `curl -d`, which mangles multibyte input before curl sends it — Node confirmed the schema computed 76 bytes and rejected correctly, and re-posting via `--data-binary @file` returned the expected 400. Test multibyte payloads from a file on this shell, never inline. **Verified end to end** against the Neon dev branch: registration 201; duplicate (incl. case/whitespace variants) 409; mismatch, short password, over-length password, bad email, blank name and non-JSON all 400 with the right message; sign-in with a registered account *and* with the seeded `demo@devstash.io` / `12345678` both reach `/dashboard` with the real user id on the session; wrong password, unknown email and an OAuth-only account (no `passwordHash`) all return `CredentialsSignin`; GitHub's authorize redirect stays well-formed; and the browser flow renders both providers on the built-in sign-in page. **Still out of scope and worth deciding before phase 3:** the dashboard continues to render the demo account because `src/lib/db/user.ts` is unchanged, so it shows "Demo User" no matter who signs in; there is **no rate limiting** on either endpoint, leaving brute-force wide open; a GitHub-linked email gets a 409 on register and cannot add a password, which is account-linking territory; and no custom login/register UI exists. Testing left four accounts in the dev branch (`test@test.com`, `two@test.com`, `cap72@test.com`, `capemoji@test.com`) — harmless, but they inflate any user count until removed.
