# Auth Security Review

**Last audited:** 2026-08-19
**Scope:** `src/auth.ts`, `src/auth.config.ts`, `src/proxy.ts`, `src/app/api/auth/[...nextauth]/route.ts`, `src/app/api/auth/register/route.ts`, `src/app/api/auth/verify/route.ts`, `src/app/api/auth/resend-verification/route.ts`, `src/app/api/auth/forgot-password/route.ts`, `src/app/api/auth/reset-password/route.ts`, `src/lib/validations/auth.ts`, `src/lib/email-verification.ts`, `src/lib/password-reset.ts`, `src/lib/rate-limit.ts`, `src/lib/feature-flags.ts`, `src/lib/account.ts`, `src/lib/db/user.ts`, `src/lib/app-url.ts`, `src/lib/resend.ts`, `src/actions/auth.ts`, `src/actions/profile.ts`, `src/app/(auth)/**` (sign-in, register, verify, forgot-password, reset-password pages), `src/app/profile/**`, `src/components/auth/**`, `src/components/profile/**`, `src/types/auth.ts`, `src/types/profile.ts`, `src/types/next-auth.d.ts`, `prisma/schema.prisma`, `.env` / `.env.production` / `.gitignore` (verification only).

## Summary

The credentials/token machinery itself is unusually careful — constant-time-cost sign-in rejection, CSRNG tokens with digest-only storage, race-safe single-use consumption on the reset path, TTL ordering, cross-flow token isolation checked in both directions, and a fail-closed feature flag are all implemented correctly and match what the code's own comments claim. The gaps that remain are the ones the project's own history already flags as "left open": no throttling on the two endpoints that matter most for brute force and abuse (sign-in, registration), a still-unfixed race in the verification token's delete path, and a couple of defense-in-depth items (session lifecycle on password change, trusting request-derived origin for emailed links) that are worth closing before this goes further. No account-takeover-by-unauthenticated-attacker was found. Counts: 0 Critical, 2 High, 3 Medium, 2 Low.

## Findings

### [HIGH] No rate limiting on credentials sign-in

- **Location:** `src/auth.ts:38-89` (the `authorize` callback), `src/app/api/auth/[...nextauth]/route.ts`
- **Issue:** `rateLimit()` (`src/lib/rate-limit.ts`) is called from `src/actions/profile.ts` and the three mail-sending routes (`resend-verification`, `forgot-password`, `reset-password`) only. Nothing calls it from `authorize` or from anywhere in the `[...nextauth]` handler chain. `POST /api/auth/callback/credentials` can be hit directly (it is what `signIn("credentials", …)` calls under the hood) with no throttle at all.
- **Impact:** An attacker can attempt unlimited username/password combinations against any account — either a slow, distributed credential-stuffing run against many accounts using breached password lists, or a targeted brute force against one account. bcrypt at 12 rounds (~220ms) is the only friction, which does not meaningfully slow a botnet running requests in parallel across many source IPs.
- **Fix:** Add a `rateLimit` check inside `authorize` (or a wrapping call before it), keyed on the submitted email (and optionally IP), before running `compare()`. Keep the ordering so the throttle check does not become a new timing oracle — check the limit and, on rejection, still perform the constant-cost bcrypt compare against `ABSENT_PASSWORD_HASH` (or return uniformly) so a rate-limited response is not distinguishable from a compare-based one by response time.

### [HIGH] No rate limiting on registration

- **Location:** `src/app/api/auth/register/route.ts:25-99`
- **Issue:** The route validates with Zod, checks for an existing email, and creates the account with no call to `rateLimit()` anywhere in the file.
- **Impact:** Combined with the 409-on-duplicate-email response (an accepted UX trade-off per the project's own notes), an attacker can enumerate registered emails at effectively unlimited speed. Independently of enumeration, unlimited registration lets an attacker force the server to perform unlimited 12-round bcrypt hashes (CPU cost) and, when `EMAIL_VERIFICATION_ENABLED=true`, unlimited outbound Resend sends (a metered, paid API) per `src/lib/email-verification.ts:62-86`.
- **Fix:** Add an IP-keyed (and optionally email-keyed) `rateLimit()` call at the top of `POST`, mirroring the pattern already used in `forgot-password/route.ts` and `resend-verification/route.ts`.

### [MEDIUM] Emailed verification/reset links trust the request's Host header when `APP_URL` is unset

- **Location:** `src/lib/app-url.ts:6-10`, consumed by `src/app/api/auth/register/route.ts:75`, `src/lib/email-verification.ts:58`, `src/lib/password-reset.ts:101`, `src/app/api/auth/verify/route.ts:20`
- **Issue:** `appOrigin()` falls back to `new URL(request.url).origin` whenever `APP_URL` is not set. In Next.js App Router route handlers, `request.url`'s origin is derived from the incoming `Host` header by default (Next.js "looks at the Host header by default" for routing — see source below), which is attacker-controlled on any request the attacker themselves sends. `APP_URL` is currently set in the working `.env` (`http://localhost:3000`), so this is not live in the environment reviewed, but the code itself has no guard against the variable being unset or against a proxy that forwards a client-supplied `Host` unmodified.
- **Impact:** If deployed without `APP_URL` set (or behind a proxy/load balancer that does not overwrite `Host`), an attacker can send a `POST /api/auth/forgot-password` (or `/register`) request with a spoofed `Host` header for a victim's email address. The email goes to the real victim, but the verification/reset link embedded in it points at the attacker's domain, so the victim clicking it hands the attacker a live 32-byte reset or verification token for their own account.
- **Fix:** Require `APP_URL` in production (throw at startup or in `appOrigin()` if `process.env.NODE_ENV === "production"` and it is unset) rather than silently falling back to request-derived origin for security-sensitive links.

### [MEDIUM] Password change does not invalidate other active sessions

- **Location:** `src/lib/account.ts:26-54` (`changeAccountPassword`), `src/auth.ts:117-134` (`jwt`/`session` callbacks)
- **Issue:** Sessions use the JWT strategy (`session: { strategy: "jwt" }`, `src/auth.ts:116`). The `jwt` callback only ever writes `token.id` at sign-in; nothing in the token is tied to the password or invalidated when `changeAccountPassword` updates `passwordHash`. Auth.js's default JWT session lifetime is 30 days. `getCurrentUser` (`src/lib/db/user.ts:31-57`) re-reads the user row on every request but only checks that the row still *exists* — it does not check the password's age or a version marker.
- **Impact:** If an attacker has obtained a valid session cookie for an account (e.g. via a stolen device, an XSS elsewhere, or a leaked cookie), the victim changing their password through the profile page's "Change Password" dialog does **not** revoke the attacker's existing session. The attacker keeps access for up to 30 days after the password that supposedly locked them out was changed.
- **Fix:** Either move to database sessions (Auth.js can then delete `Session` rows on password change / "sign out everywhere"), or add a version/timestamp claim to the JWT (e.g. a `pwUpdatedAt` written to the token at sign-in and compared against the user row's `updatedAt` on each request in a `session`/`jwt` callback, rejecting stale tokens).

### [MEDIUM] Response-time enumeration on `forgot-password` and `resend-verification`

- **Location:** `src/app/api/auth/forgot-password/route.ts:69-86`, `src/app/api/auth/resend-verification/route.ts:74-88`
- **Issue:** Both routes return one generic body for every outcome (unknown address, OAuth-only account, already-verified account, real send) — good. But the conditional branch (`if (user?.passwordHash) { await issuePasswordReset(...) }` / `if (user?.passwordHash && !user.emailVerified) { await issueEmailVerification(...) }`) awaits an outbound network call to Resend *inline*, before responding, only on the branch where mail is actually sent.
- **Impact:** A registered, password-having account (forgot-password) or a registered-but-unverified account (resend-verification) takes measurably longer to answer than an unknown address, because the former waits on a live network round trip to Resend and the latter does not. This lets an attacker distinguish registered from unregistered emails, and — on resend-verification — distinguish verified from unverified accounts, by timing alone, even though the response bodies are identical. This is the same class of issue the project already fixed for sign-in (`ABSENT_PASSWORD_HASH` in `src/auth.ts`) but left open here, as the project's own history notes.
- **Fix:** Either fire the Resend call without awaiting it before responding (accepting that failures are then unobservable to the caller, which is already true of the response body), or pad the "nothing to send" branch with an equivalent-cost dummy delay/await so both paths take comparable wall-clock time.

### [LOW] `consumeVerificationToken` uses `delete` instead of `deleteMany`, unlike its reset-flow sibling

- **Location:** `src/lib/email-verification.ts:94-138`, specifically line 113: `await prisma.verificationToken.delete({ where: { token: digest(token) } });`
- **Issue:** Prisma's `delete` throws `PrismaClientKnownRequestError` (`P2025`) when the row no longer exists. `resetPasswordWithToken` in `src/lib/password-reset.ts:184-190` was explicitly fixed to use `deleteMany` guarded on `count` for exactly this reason (documented in that file's own comment), but `consumeVerificationToken` was not brought in line — it still calls `findUnique` then `delete`, leaving a window between the two calls.
- **Impact:** Two concurrent `GET /api/auth/verify?token=…` requests for the same link (e.g. an email client prefetching the link, or a double click) race: the first delete succeeds, the second throws an uncaught `P2025` that neither `consumeVerificationToken` nor the calling route (`src/app/api/auth/verify/route.ts`) catches, producing an unhandled exception and a 500 response instead of the intended graceful `"invalid"` outcome. This is a reliability defect, not an auth bypass — the token is still consumed exactly once either way.
- **Fix:** Mirror the reset flow: replace the `delete` with `deleteMany` guarded on `count === 0`, matching `resetPasswordWithToken`.

### [LOW] Rate-limit IP key trusts the first `X-Forwarded-For` entry unconditionally

- **Location:** `src/lib/rate-limit.ts:38-42`
- **Issue:** `callerKey()` takes `x-forwarded-for.split(",")[0]`. This is only the real client IP if the edge proxy in front of the app *overwrites* (rather than appends to) any client-supplied `X-Forwarded-For` header. If the deployment's proxy appends to whatever the client sends, a client can prepend an arbitrary first entry (e.g. `X-Forwarded-For: 1.2.3.4`) and have it read back as the "caller," letting them rotate through fake IPs to bypass the per-IP limiters on `resend-verification`, `forgot-password` and `reset-password`.
- **Impact:** Reduces the effectiveness of the existing IP-keyed limiters to whatever the per-email limiter still catches (3/15min on the two mail endpoints; none on `reset-password`, which is IP-only). This is already the behavior the code's own comment acknowledges ("spoofable, which is another reason this is a brake rather than a quota") — flagged here to make the specific mechanism (wrong end of the header, not "IP is spoofable" in the abstract) explicit and to note it compounds with the two High findings above once sign-in/register gain rate limiting.
- **Fix:** Confirm the deployment platform's edge (Vercel, or whatever fronts production) sets `X-Forwarded-For` by overwriting rather than appending; if not guaranteed, prefer a platform-provided trusted-IP header (e.g. Vercel's `x-real-ip` / `x-vercel-forwarded-for` conventions) over a raw, client-suppliable header.

## Passed Checks

- **Uniform-cost sign-in rejection.** `src/auth.ts:20-21,65-68` compares against a constant 12-round `ABSENT_PASSWORD_HASH` whenever there is no real hash to match (unknown email or OAuth-only account), so every rejection path costs one bcrypt compare — closing the timing oracle a naive early-return would create.
- **`emailVerified` gate ordered after the password check**, not before (`src/auth.ts:74-80`), so gating on verification status does not reopen the timing oracle the constant-hash comparison closes.
- **Password hashing.** bcryptjs at 12 rounds everywhere a password is written — register (`src/app/api/auth/register/route.ts:12,58`), reset (`src/lib/password-reset.ts:19,208`), and change-password (`src/lib/account.ts:7,50`) all use the same cost factor.
- **bcrypt's 72-byte truncation is defended, not truncated silently.** `passwordSchema` in `src/lib/validations/auth.ts:28-36` rejects passwords over 72 UTF-8 bytes (counted via `TextEncoder`, not `.length`) rather than letting bcrypt drop the excess.
- **The password hash never leaves the data layer.** `getCurrentUser` (`src/lib/db/user.ts:31-57`) destructures `passwordHash` out of the query result and exposes only a derived `hasPassword: boolean`; `authorize`'s return value (`src/auth.ts:82-87`) and the register route's response (`src/app/api/auth/register/route.ts:64`) both select only `id`/`name`/`email`/`image`.
- **Password change requires the current password**, checked server-side via `compare()` against the stored hash before any update (`src/lib/account.ts:44-50`), not merely trusted because a session exists.
- **CSPRNG tokens with sufficient entropy.** Both verification and reset tokens are `randomBytes(32)` (`node:crypto`) — never `Math.random` — in `src/lib/email-verification.ts:47` and `src/lib/password-reset.ts:86`.
- **Only a digest is stored.** Both flows store `sha256(token)`, never the raw token, so a database read of `VerificationToken` cannot verify or reset an account (`src/lib/email-verification.ts:26-28`, `src/lib/password-reset.ts:65-67`).
- **Reset tokens are race-safe single-use.** `resetPasswordWithToken` uses `deleteMany` guarded on `count` rather than `delete` (`src/lib/password-reset.ts:184-190`), so two concurrent submits of one token resolve to one success and one clean "invalid" rather than a 500.
- **Issuing a new token invalidates the old one**, in both flows — `deleteMany` by identifier before `create` (`src/lib/email-verification.ts:49-50`, `src/lib/password-reset.ts:88-91`).
- **Reset TTL is materially shorter than verification TTL.** 1 hour (`src/lib/password-reset.ts:13`) vs 24 hours (`src/lib/email-verification.ts:8`), justified in-code by the reset token being account-takeover-capable.
- **Cross-flow token isolation, checked in both directions.** Reset tokens are stored under an `identifier` prefixed `password-reset:`; `consumeVerificationToken` rejects (and leaves in place) any token whose identifier carries that prefix (`src/lib/email-verification.ts:106-111`), and `checkPasswordResetToken`/`resetPasswordWithToken` reject any token whose identifier does *not* carry it (`src/lib/password-reset.ts:143-148,171-177`) — a token minted by one flow cannot be spent by the other's endpoint.
- **A completed reset leaves the account coherent.** `resetPasswordWithToken` sets `emailVerified` if it was not already set (`src/lib/password-reset.ts:205-213`), so a reset cannot leave an account able to sign in with a new password while still failing the verification gate.
- **Expiry enforced at consume time**, not merely at issue time, for both flows (`src/lib/email-verification.ts:115-117`, `src/lib/password-reset.ts:192-194`), and the row is still deleted even when expired so a stale token cannot be retried.
- **Mutation split from rendering for reset.** `/reset-password` (`src/app/(auth)/reset-password/page.tsx`) only reads the token via `checkPasswordResetToken` (read-only); the actual spend happens in `POST /api/auth/reset-password`, so a page render, prefetch, or reload cannot burn the token.
- **OAuth-only accounts cannot acquire a password via the reset flow.** `forgot-password/route.ts:78` only issues a reset when `user?.passwordHash` is truthy — a GitHub-only account gets no mail, so the reset flow cannot be used as a back door to hand it a password (which would be account linking, not a reset).
- **Feature flag fails closed.** `isEmailVerificationEnabled()` (`src/lib/feature-flags.ts:19-23`) defaults to enabled for any unset or unrecognized value — an incomplete environment keeps the verification requirement rather than silently dropping it.
- **New accounts registered while the flag is off are stored already verified** (`src/app/api/auth/register/route.ts:62`), so flipping the flag back on later cannot retroactively lock them out.
- **Email normalization is consistent.** `emailSchema` in `src/lib/validations/auth.ts:8-12` (`trim().toLowerCase()`) is the single schema reused by sign-in, registration, resend, forgot-password and reset — a `Test@Example.com` registration and a `test@example.com` sign-in resolve to the same row.
- **Enumeration is deliberately suppressed where it matters**, and named where it is an accepted trade-off: `forgot-password` and `resend-verification` return one generic body regardless of account state (`src/app/api/auth/forgot-password/route.ts:21-24,86`, `src/app/api/auth/resend-verification/route.ts:25-28,90`); the 409 on `/api/auth/register` is a deliberate, documented UX trade-off (an attacker still learns an email is registered, but only via that one endpoint, not fanned out across the mail-sending routes).
- **Profile page and mutations re-check the session server-side.** `/profile` calls `getCurrentUser()` and redirects on `null` (`src/app/profile/page.tsx:19-27`) in addition to the proxy matcher — covering the case the proxy structurally cannot: a JWT that still verifies against a deleted row. `changePassword` and `deleteAccountAction` both derive `userId` from `getCurrentUserId()` (session-derived), never from client input (`src/actions/profile.ts:46,90`).
- **Delete-account cleans up rows that do not cascade.** `VerificationToken` has no relation to `User`; `deleteAccount` explicitly clears both the plain and `password-reset:`-prefixed identifiers for the account's email before removing the user row (`src/lib/account.ts:80-92`), and both deletes use `deleteMany`/`count` rather than `delete`, avoiding the race the verify-flow finding above still has.
- **No session survives account deletion.** `deleteAccountAction` calls `signOut({ redirectTo: SIGN_IN_PATH })` immediately after a successful deletion (`src/actions/profile.ts:101`).
- **Change-password is rate-limited on a non-spoofable key.** `src/actions/profile.ts:62-66` keys the limiter on the session-derived `userId`, not on IP or any client-supplied value.
- **Duplicate-registration race is backstopped at the database.** Beyond the pre-check `findUnique`, `register/route.ts:88-93` catches Prisma's `P2002` unique-constraint violation on `User.email` and returns the same 409, closing the TOCTOU gap between the check and the insert.
- **Every route handler and server action reviewed validates with Zod before touching Prisma** — register, resend-verification, forgot-password, reset-password, change-password and sign-in all parse through a schema in `src/lib/validations/auth.ts` first.

## Notes / Unverified

- **OAuth email casing.** Nothing in `src/auth.config.ts` or `src/auth.ts` normalizes the email Auth.js's Prisma adapter receives from GitHub's profile response before creating/matching a `User` row (only the credentials-flow Zod schemas normalize). In practice GitHub's API returns lowercase addresses, and Auth.js's default behavior throws `OAuthAccountNotLinked` rather than silently merging accounts on an exact-match email, so this is unlikely to be exploitable — flagged here only as unverified rather than as a finding, since it depends on GitHub's API behavior and Auth.js's internal matching, neither of which was exercised live in this review.
- **The in-memory rate limiter is explicitly a "brake, not a quota"** by the project's own design (per-process state, lost on restart, no shared store across serverless instances) — noted in `src/lib/rate-limit.ts`'s own comments. This is an accepted trade-off for the endpoints that do have it, not treated as a new defect beyond the two High findings (missing entirely on sign-in/register) and the Low finding (spoofable key) above.
- **`.env` is not committed.** Verified `.gitignore:34-35` excludes `.env*` except `.env.example`; the working-tree `.env` and `.env.production` files carrying real credentials are local-only, not a repository defect.

Sources consulted for library-behavior claims: [Next.js routing looks at the Host header by default](https://github.com/vercel/next.js/discussions/34571), [Auth.js default JWT session maxAge is 30 days](https://next-auth.js.org/configuration/options).
